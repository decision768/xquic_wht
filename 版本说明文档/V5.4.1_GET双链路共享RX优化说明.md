# V5.4.1 GET 双链路共享 RX 优化说明

## 1. 版本信息

- 发布标识：`V5.4.1`
- 优化主题：双链路 GET 共享 RX 队列即时通知与双侧限额
- 当前实现快照：分支 `v5.5.3`，基础提交 `631cbbe8`，叠加当前工作区未提交修改
- 生产目标：Linux/ARM
- 修改范围：客户端 `mini_client`

> `V5.4.1` 是本次优化的发布标识，不表示当前 Git 分支或基础提交已切换为同名版本。

## 2. 问题背景

原客户端接收架构为：

```text
每路径 RX 线程
→ 共享 FIFO 队列
→ 通知 pipe
→ Libevent/XQUIC 引擎线程
→ xqc_engine_packet_process()
→ xqc_engine_finish_recv()
→ ACK 与 HTTP/3 回调
```

双链路 GET 的主要问题不是服务端没有发送数据，而是客户端 RX 通知和队列处理存在跨路径耦合：

1. RX 线程成为通知所有者后，旧逻辑可能继续读取当前 socket，直到本批结束或读到 `EAGAIN` 才通知引擎线程。
2. 另一条路径虽然已经将数据放入共享队列，却因为共享 `rx_notify_pending` 已置位而不能再次通知。
3. 快路径持续可读时，通知和 `xqc_engine_finish_recv()` 被推迟，导致数据包处理、ACK 反馈、拥塞窗口增长和调度反馈变慢。
4. 生产者和消费者单轮工作量过大时，会进一步放大快路径对 CPU 和 XQUIC 引擎线程的占用。

POST 方向的主要数据流由客户端主动发送，不依赖相同的 GET 下行数据接收和 ACK 反馈节奏，因此该问题在双链路 GET 中表现得更明显。

## 3. 优化目标

本版本采用保守方案，保留“每路径 RX 线程＋共享 FIFO＋通知 pipe”的现有架构，只修复错误通知时序并限制单轮工作量：

- 第一个数据包成功入队后立即通知 XQUIC 引擎线程。
- 限制每个 RX 生产者的单批收包数量和时间。
- 限制引擎线程单轮消费共享队列的数量和时间。
- 保持每轮一次 `xqc_engine_finish_recv()`，缩短 ACK 反馈间隔。
- 完善路径失败、线程退出、路径重建和连接关闭的资源生命周期。
- 增加每秒及最终 RX 诊断日志，便于确认优化是否真正生效。

## 4. 核心参数

```c
#define CLIENT_RX_PRODUCER_MAX_PACKETS 128
#define CLIENT_RX_PRODUCER_MAX_US      1000
#define CLIENT_RX_DRAIN_MAX_PACKETS    256
#define CLIENT_RX_DRAIN_MAX_US         2000
```

含义如下：

| 参数 | 含义 |
|---|---|
| `CLIENT_RX_PRODUCER_MAX_PACKETS` | 单个路径 RX 线程每批最多接收 128 个 UDP 包 |
| `CLIENT_RX_PRODUCER_MAX_US` | 单个生产批次最多占用约 1000 μs |
| `CLIENT_RX_DRAIN_MAX_PACKETS` | XQUIC 引擎线程每轮最多处理 256 个队列包 |
| `CLIENT_RX_DRAIN_MAX_US` | 单轮队列处理预算约 2000 μs |

达到生产者限额后，线程返回外层 `poll()`。如果 socket 仍然可读，level-triggered `poll()` 会再次唤醒，不会丢失后续数据。

达到消费者限额且共享队列仍有数据时，由 XQUIC 引擎线程通过 `event_active()`续触发下一轮处理。

## 5. 主要优化内容

### 5.1 首包入队后即时通知

新的通知顺序为：

```text
recvfrom() 成功
→ 数据包复制并加入共享 FIFO
→ 在队列锁内将 rx_notify_pending 从 0 改为 1
→ 当前线程立即 write(pipe)
→ 继续处理本批后续数据包
```

只有成功将 `rx_notify_pending` 从 `0` 改为 `1` 的生产者负责写 pipe。其他生产者只增加 `notify_skip`，避免重复通知风暴。

pipe 错误处理：

- `EINTR`：立即重试。
- `EAGAIN/EWOULDBLOCK`：保持 `rx_notify_pending=1`，因为 pipe 中已经存在尚未消费的通知。
- 其他错误：累计 `notify_error`，清除 pending；后续入队、RX 线程 `poll()` 超时检查或路径重试事件会再次尝试通知。

RX 线程不调用 `event_active()`。Libevent 事件的续触发仍由 XQUIC 引擎线程负责。

### 5.2 生产者限额

每次 `poll()` 唤醒后：

- 最多读取 128 个包。
- 最多执行约 1000 μs。
- 每个成功入队的首个待通知包立即写 pipe。
- `EAGAIN/EWOULDBLOCK` 结束当前批次。
- `EINTR` 在时间预算内重试。
- 其他 `recvfrom()` 错误计数后结束当前批次。
- `POLLERR/POLLHUP/POLLNVAL` 或 `poll()` 真实错误被视为 RX 线程异常退出，并交由引擎线程处理路径故障。

### 5.3 消费者限额

共享队列消费保持“锁内摘取、锁外处理”：

1. 在 `rx_queue_lock` 内从 FIFO 头部摘取一个包。
2. 立即释放队列锁。
3. 在锁外调用 `xqc_engine_packet_process()`。
4. 在锁外释放数据包内存。

单轮最多处理 256 包或约 2000 μs。本轮至少有一个包成功提交给 XQUIC 时，调用一次 `xqc_engine_finish_recv()`。

这可以避免一个超大共享队列长时间独占 XQUIC 引擎线程，使 ACK、定时器、HTTP/3 回调和路径调度更及时地执行。

### 5.4 地址快照与路径槽复用

每个入队包保存独立的：

- 本地地址和长度。
- 对端地址和长度。
- 路径槽索引。
- 路径 generation。
- 实际收包时间。

因此，即使数据包等待期间原路径被删除或路径槽被重建，队列消费者也不会引用已经释放或已被覆盖的路径地址内存。

本地 socket 地址通过 `getsockname()` 在线程启动前完成初始化，并使用 `sockaddr_storage` 保存。RX 线程运行期间路径地址保持只读，消除了 RX 线程和引擎线程同时读写地址字段的竞争。

### 5.5 线程与路径生命周期

所有会关闭或替换路径 socket 的流程统一遵守：

```text
停止 RX 线程
→ pthread_join()
→ 标记路径不可用
→ 删除 Libevent socket 事件
→ close(fd)
→ fd 置为 -1
→ 根据连接状态关闭路径、重建路径或关闭连接
```

修复内容包括：

- GET 和 POST 的路径写失败都必须先停止对应 RX 线程。
- 防止旧 RX 线程继续轮询已关闭或已被新路径复用的 fd。
- 握手未完成或最后一条有效路径失效时关闭整个连接，不再错误尝试单路径重建。
- 仍有其他有效路径且握手完成时，关闭故障路径并启动快速重建。
- `prepare_user_path()` 在替换 socket 前再次确保旧 RX 线程已经回收。
- `rx_thread_running`、`rx_threads_running`、`rx_thread_failed` 和 `last_socket_time` 使用一致的原子访问。
- RX 线程缓冲区只在线程启动前分配，在线程 join 后释放。

### 6.5 延迟桶

RX 包等待和 `finish_recv()` 间隔使用固定桶：

```text
≤50、≤100、≤250、≤500、≤1000、≤5000、≤20000、>20000 μs
```

日志中的 `20001` 是“超过 20000 μs”的标记，不代表真实最大值只有 20001 μs；真实最大值由对应 `*_max` 字段给出。

周期日志每秒最多输出一次。下载完成、超时和连接关闭时会强制输出最终汇总。

## 8. 未修改范围

本版本没有修改：

- multipath scheduler 和 adaptive 决策逻辑。
- BBR/拥塞控制参数。
- HTTP/3 分片和并发流控制。
- 服务端 GET 文件发送逻辑。
- 客户端异步写盘算法。
- 共享 FIFO 和每包 `malloc/memcpy/free` 的基础架构。

因此，本版本用于优先验证“客户端延迟通知和无界单轮处理”是否是双链路 GET 吞吐受限的主要原因。

## 9. 预期效果

- 首个入队包不再等待当前 socket 排空后才通知引擎。
- 快路径不能无限持续占用 RX 生产线程或 XQUIC 消费线程。
- `packet_wait_us_p99` 和 `finish_gap_us_p99` 明显下降。
- ACK 反馈更及时，双链路拥塞窗口和调度反馈更容易持续增长。
- 慢路径收到的数据不会因为另一条快路径持有通知状态而长期滞留。
- 单链路模式仅增加轻量预算判断，不应出现明显性能回退。

## 10. 验证建议

目标 Linux/ARM 环境应至少执行：

1. 单链路 1、单链路 2、双链路分别下载 100 MB，并校验 SHA-256。
2. 快路径持续满载、慢路径间歇到包，检查两条路径的 `packets` 是否持续增长。
3. 传输中删除并重建任一路径。
4. 覆盖 `EAGAIN`、`EINTR`、pipe 满、内存分配失败和真实 socket 错误。
5. 修改前后至少进行 10 轮交替 GET 测试，POST 作为未修改方向的对照组。

重点验收：

- `notify_error=0`。
- 正常结束时 `q_cur=0`。
- `drain_max_pkts` 不超过 256。
- 正常批次的 `batch_max_pkts` 不超过 128。
- 双链路两个 `diag_rx_path packets` 均持续增长。
- GET 队列等待 p99 相比旧版本下降至少 25%。
- 双链路 GET 吞吐提升至少 5%，或相同吞吐下客户端 CPU 下降至少 10%。
- 单链路吞吐回退不超过 3%。
- 无崩溃、死锁、忙循环、UAF、重复释放或 fd 重复关闭。

## 11. 已知边界

本版本仍然保留共享 FIFO，因此：

- 不能彻底消除跨路径 FIFO 队头阻塞。
- 不提供严格的逐路径公平消费。
- 每包动态内存分配和复制仍会产生 CPU 与内存管理开销。

如果日志证明通知延迟、队列等待和 `finish_recv()` 间隔已经明显下降，但双链路 GET 仍长期失衡，应将后续范围限定为：

1. 每路径独立 RX 队列和轮转消费；或
2. adaptive 带宽估算及调度反馈修正。

不应在本补丁中同时扩大到调度器和拥塞控制修改。
