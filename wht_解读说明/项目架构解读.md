# xquic_wht 项目架构解读

本文档说明 `xquic_wht` 的整体架构、模块职责和主要调用链。配套架构图见 [项目架构图.mmd](./项目架构图.mmd)。

## 总体架构

项目可以分成五层：

| 层级 | 对应路径 | 主要职责 |
| --- | --- | --- |
| 应用/测试层 | `mini/`、`GX/`、`interop/`、`scripts/` | 调用 XQUIC API，提供示例程序、设备压测、互操作测试和日志分析。 |
| 公共 API 层 | `include/xquic/` | 对应用暴露 QUIC engine、连接、流、HTTP/3 请求等接口。 |
| 协议实现层 | `src/http3/`、`src/transport/` | 实现 HTTP/3/QPACK 和 QUIC 传输层。 |
| 算法与安全层 | `src/congestion_control/`、`src/tls/` | 实现拥塞控制、TLS 适配、HKDF、加解密接口。 |
| 基础设施与依赖层 | `src/common/`、SSL、libevent、系统 socket | 提供日志、时间、随机数、容器、事件循环、UDP socket 和加密库。 |

核心关系是：应用不直接操作 `src` 内部结构，而是通过 `include/xquic` 的公共 API 创建 engine、连接和 HTTP/3 请求；XQUIC 内部再把 HTTP/3 请求映射到 QUIC stream，并通过 UDP socket 收发包。

## 核心库内部模块

### 1. 公共 API 层

`include/xquic/xquic.h` 是 QUIC engine 的主入口，定义：

- client/server engine 类型。
- 事件定时器、CID 生成、日志、keylog 等回调。
- engine、connection、stream、datagram、packet process 等接口。
- 连接配置、传输参数、统计和错误处理相关类型。

`include/xquic/xqc_http3.h` 是 HTTP/3 API，定义：

- H3 connection 和 request 回调。
- Header 结构与编码标志。
- request 读写通知。
- H3 请求发送、接收和连接控制相关接口。

应用侧的典型接入方式是同时包含这两个头文件：先创建 XQUIC engine，再初始化 HTTP/3 context，最后创建 H3 连接和请求。

### 2. QUIC 传输层: `src/transport`

传输层是核心协议状态机，主要职责包括：

- `xqc_engine.*`：engine 生命周期、主逻辑调度、外部 UDP 包入口。
- `xqc_conn.*`：连接状态、握手、关闭、路径和 stream 管理。
- `xqc_stream.*`：QUIC stream 收发、流控、状态推进。
- `xqc_packet*.*`：packet in/out 表示、组包、解析和发送队列。
- `xqc_frame*.*`：QUIC frame 生成、解析和处理。
- `xqc_send_ctl.*`、`xqc_send_queue.*`：发送控制、重传、拥塞控制衔接。
- `xqc_cid.*`：Connection ID 管理。
- `xqc_timer.*`：协议定时器。
- `xqc_multipath.*`、`scheduler/`：多路径连接和路径调度。
- `reinjection_control/`：多路径重注入策略。
- `xqc_datagram.*`：QUIC Datagram 支持。
- `xqc_fec.*`、`fec_schemes/`：可选 FEC 支持。

传输层向上承载 HTTP/3，向下依赖 socket 发送 UDP 包，并在发送控制中调用拥塞控制算法。

### 3. HTTP/3 与 QPACK: `src/http3`

HTTP/3 层把应用请求转换为 QUIC stream 上的 HTTP/3 frame：

- `xqc_h3_ctx.*`：HTTP/3 context 初始化与管理。
- `xqc_h3_conn.*`：H3 connection 生命周期和控制流。
- `xqc_h3_request.*`：请求创建、发送 headers/body、接收 headers/body。
- `xqc_h3_stream.*`：H3 stream 与 QUIC stream 的衔接。
- `frame/`：HTTP/3 frame 定义和编解码。
- `qpack/`：Header 压缩和解压，包括静态表、动态表和指令处理。
- `xqc_h3_ext_dgram.*`、`xqc_h3_ext_bytestream.*`：HTTP/3 扩展能力。

当应用调用 `xqc_h3_request_send_headers` 或 `xqc_h3_request_send_body` 时，HTTP/3 层负责生成 frame，最终交给传输层 stream 发送。

### 4. TLS 与加密: `src/tls`

TLS 层隔离 XQUIC 与具体 SSL 实现：

- `xqc_tls.*`：TLS 状态和握手衔接。
- `xqc_tls_ctx.*`：TLS 上下文管理。
- `xqc_crypto.*`：加解密抽象。
- `xqc_hkdf.*`：密钥派生。
- `xqc_null_crypto.*`：无加密或测试场景支持。
- `boringssl/` 和 `babassl/`：分别适配 BoringSSL 与 BabaSSL/Tongsuo。

当前 `CMakeLists.txt` 默认 `SSL_TYPE=babassl`，会选择 `src/tls/babassl` 下的实现。

### 5. 拥塞控制: `src/congestion_control`

拥塞控制模块被传输层发送控制调用，决定发送窗口、带宽估计和发送节奏。默认源码包含 Cubic、BBR、采样和窗口过滤，其他算法通过 CMake 选项追加：

- 默认：`xqc_cubic.c`、`xqc_bbr.c`、`xqc_sample.c`、`xqc_window_filter.c`。
- 可选：`xqc_new_reno.c`、`xqc_bbr2.c`、`xqc_copa.c`、`xqc_unlimited_cc.c`。

### 6. 基础工具: `src/common`

`src/common` 是协议层的基础设施，包括：

- 日志和 event log。
- 时间、随机数、字符串工具。
- Hash、链表、队列、红黑树、FIFO。
- buffer、内存池、对象管理。
- QPACK/协议编码依赖的 huffman、varint、ring buffer 等工具。

该层不表示业务协议，但被 HTTP/3、transport、TLS 广泛使用。

## mini 客户端/服务端调用链

### mini_client

`mini_client` 是最重要的应用侧参考。主调用链如下：

1. `mini/mini_client_main.c` 中 `main` 创建 `xqc_mini_cli_ctx_t` 和 `xqc_mini_cli_args_t`。
2. `xqc_mini_cli_init_env` 初始化环境、日志、配置和 libevent。
3. `xqc_mini_cli_init_xquic_engine` 调用 `xqc_engine_create(XQC_ENGINE_CLIENT, ...)`。
4. `xqc_mini_cli_init_engine_ctx` 初始化 HTTP/3 callbacks，并调用 `xqc_h3_ctx_init`。
5. `xqc_mini_cli_user_conn_create` 创建用户连接上下文。
6. `xqc_mini_cli_main_process` 建立连接，创建请求流，发起 HTTP/3 请求。
7. socket 事件触发后，收到 UDP 包调用 `xqc_engine_packet_process`。
8. 定时器或事件回调中调用 `xqc_engine_main_logic` 推进状态机。
9. `mini_client_cb.c` 处理 H3 连接和请求回调，输出统计结果。

在多网卡测试场景中，`mini_client.c` 中存在 `SO_BINDTODEVICE` 绑定逻辑，配置中的接口名会影响实际走哪张网卡。

### mini_server

`mini_server` 是服务端示例。主调用链如下：

1. `mini/mini_server_main.c` 中 `main` 初始化上下文和参数。
2. `xqc_mini_svr_init_xquic_engine` 调用 `xqc_engine_create(XQC_ENGINE_SERVER, ...)`。
3. 初始化 HTTP/3 callbacks，并调用 `xqc_h3_ctx_init`。
4. 创建 UDP socket 和 libevent 事件。
5. 收到 UDP 包后调用 `xqc_engine_packet_process`。
6. `mini_server_cb.c` 在请求回调中读取 headers/body，并发送响应 headers/body。
7. libevent 循环持续驱动 engine 主逻辑。

## GX 设备压测架构

`GX` 工作流是在 XQUIC/mini 之上的设备压测层，关注多 5G 链路和聚合模式。

### 角色划分

| 角色 | 文件 | 说明 |
| --- | --- | --- |
| 压测编排 | `GX/stress_gx.py` | 控制测试顺序和 5G 模块上下线。 |
| 设备控制 | `GX/serial_at.py` | 通过 COM 串口发 AT 命令控制模块。 |
| 远端执行 | `GX/ssh_gx.py` | SSH 到目标设备，执行远端 `mini_client`。 |
| 结果归档 | `GX/gx_stress_*.log`、`GX/log*/` | 保存主流程日志和 summary 结果。 |
| 被测程序 | 远端 `/oemdata/gx/xquic_file/mini_client` | 实际执行 HTTP/3/QUIC 上传下载的客户端。 |

### 压测数据流

1. `stress_gx.py` 初始化两个串口控制器：5G1 和 5G2。
2. 先运行 `Agg`，表示聚合模式。
3. 关闭 5G1 后运行 `5G2`。
4. 恢复 5G1 后再次运行 `Agg`。
5. 关闭 5G2 后运行 `5G1`。
6. 每个模式调用 `ssh_gx.single_test(mode)`。
7. `ssh_gx.py` 分别执行上传和下载。
8. 上传时切到远端 `client_config_post*.txt`，下载时切到远端 `client_config_get*.txt`。
9. 运行远端 `./mini_client`。
10. 解析 stdout 中的吞吐统计行。
11. 将结果写入 `GX/log/{tag}_summary_{post|get}_{HHMMSS}.log`。

这个工作流的关键边界是：本地 Python 脚本只负责编排和解析，真正的 QUIC/HTTP3 收发发生在远端设备上的 `mini_client` 进程中。

## 构建和链接关系

`CMakeLists.txt` 将源码分为五组：

- `HTTP3_SOURCES`
- `TRANSPORT_SOURCES`
- `TLS_SOURCE`
- `COMMON_SOURCES`
- `CONGESTION_CONTROL_SOURCES`

这些源码组合成：

- `xquic-static`：静态库。
- `xquic`：动态库。

开启 `XQC_ENABLE_TESTING` 时，`mini/CMakeLists.txt` 会构建：

- `mini_client`
- `mini_server`

它们链接：

- `xquic-static`
- SSL 库
- libevent
- zlog
- pthread/math/dl 等系统库

当前构建脚本有明显的目标平台倾向：

- `CMAKE_SYSTEM_NAME` 写为 Linux。
- `CMAKE_SYSTEM_PROCESSOR` 写为 aarch64。
- 编译器路径指向 `/opt/crosstools/toolchain/gcc/usr/bin/aarch64-oe-linux`。
- sysroot 指向 `/opt/crosstools/sysroot`。

因此，在 Windows 工作区直接阅读没有问题；直接构建需要具备对应 Linux/aarch64 交叉编译环境和 CMake 预期的第三方依赖路径。

## 关键运行时关系

### 应用到协议栈

```text
mini_client / mini_server
  -> include/xquic/xquic.h
  -> include/xquic/xqc_http3.h
  -> src/http3
  -> src/transport
  -> src/tls + src/congestion_control + src/common
  -> SSL library + UDP socket
```

### GX 到远端 mini_client

```text
GX/stress_gx.py
  -> GX/serial_at.py 控制 5G1/5G2 上下线
  -> GX/ssh_gx.py SSH 到设备
  -> /oemdata/gx/xquic_file/client_config*.txt
  -> /oemdata/gx/xquic_file/mini_client
  -> stdout 统计行
  -> GX/log/*_summary_*.log
```

### 收包处理链

```text
UDP socket readable
  -> mini socket callback
  -> xqc_engine_packet_process
  -> packet parser
  -> frame parser
  -> connection / stream state update
  -> HTTP/3 request callback
```

### 发包处理链

```text
应用调用 H3 request send
  -> HTTP/3 frame encoding
  -> QUIC stream send buffer
  -> send control / congestion control
  -> packet out
  -> socket send
```

## 调试定位建议

### 看 API 使用

优先看：

- `mini/mini_client_main.c`
- `mini/mini_client.c`
- `mini/mini_client_cb.c`
- `include/xquic/xquic.h`
- `include/xquic/xqc_http3.h`

### 看协议状态机

优先看：

- `src/transport/xqc_engine.c`
- `src/transport/xqc_conn.c`
- `src/transport/xqc_stream.c`
- `src/transport/xqc_send_ctl.c`
- `src/http3/xqc_h3_request.c`

### 看 GX 压测问题

优先看：

- `GX/stress_gx.py`：确认 5G1/5G2/Agg 阶段是否执行。
- `GX/ssh_gx.py`：确认远端配置切换、`mini_client` 执行和 summary 写入条件。
- 远端 `/oemdata/gx/xquic_file/client_config*.txt`：确认接口、服务器、上传下载参数。
- `GX/gx_stress_*.log`：确认阶段时间线。
- `GX/log*/...summary...log`：确认是否解析到吞吐统计。

## 当前仓库的几个注意点

- `GX` 下日志和 summary 文件很多，不应作为架构阅读主线。
- `lib` 很大且包含第三方源码/对象/预编译文件，排查依赖时再进入。
- 当前 CMake 引用的是 `third_party/...` 路径，但顶层看到的是 `lib/aarch64` 和 `lib/x86`。如果构建失败，应优先核对依赖目录布局。
- `mini_client_main.c` 和 `mini_server_main.c` 中命令行解析逻辑有部分注释，当前行为更依赖默认配置或配置文件初始化。
- `README.md` 部分中文显示为乱码，可能是编码或历史转换问题；不影响源码结构判断，但对用户文档阅读有影响。
