# XQUIC 技术导论与网络基础

本文介绍理解、配置、扩展和调试 XQUIC `mini_client` 与 `mini_server` 所需的网络基础知识。

本文与 [XQUIC Mini 客户端与服务器开发指南](./QUIC2Path_Mini_Client_Server_Developer_Guide_zh-CN_v2.md) 配套使用：

- 本文解释系统**为什么**这样工作；
- 《开发指南》说明代码**如何**构建、配置、运行和集成。

本文面向熟悉 C/C++ 和 Linux，但尚未系统掌握 QUIC、HTTP/3、多路径传输与拥塞控制的开发者和工程师，也适合希望了解文件如何从应用层逐层拆分、经无线链路传输并在接收端还原的读者。

> **适用范围**
>
> 当前 XQUIC 实现采用：
>
> - 基于 XQUIC 的 HTTP/3；
> - 一条 QUIC 连接，同时使用最多两条活跃网络路径；
> - 两张分别接入不同 5G 运营商的网卡；
> - GET 下载与 POST 上传；
> - 基于文件区间的多流传输；
> - 可配置的路径调度；
> - 可配置的拥塞控制；
> - 由 Libevent 驱动的 XQUIC 引擎。

```text
├───────────────────────────────────┤                   ├─────────────────────────────┤

├───────────────────────────────────┤                   ├─────────────────────────────┤

└───────────────────────────────────┘                   └─────────────────────────────┘
```

系统在逻辑上只有**一条 QUIC 连接**，但连接中的数据包可以同时经由两条不同的 5G 网络路径传输。

两条路径可能具有不同的：

- 带宽；
- 往返时延；
- 时延抖动；
- 丢包率；
- 切换行为；
- 覆盖质量；
- 排队时延；
- 运营商核心网路由。

因此，系统需要解决的核心控制问题是：

\[
对每一份待发送数据，应该选择哪条路径？该路径又允许发送多快？
\]

这两个问题由不同模块回答：

\[
\boxed{
\begin{aligned}
\text{调度器} &: \text{下一份数据应该通过哪条路径发送？}\\
\text{拥塞控制} &: \text{每条路径当前允许发送多少、发送多快？}
\end{aligned}
}
\]

# 2. 网络协议栈

文件不会以一个完整对象的形式直接在网络中传输。数据会逐层经过多个协议，每一层都会添加本层元数据或执行相应转换。

```text
应用文件
    ↓
XQUIC 文件区间/应用分段
    ↓
HTTP/3 请求体或响应体
    ↓
QUIC 流字节与 STREAM 帧
    ↓
由 TLS 1.3 保护的 QUIC 数据包
    ↓
UDP 数据报
    ↓
IP 数据包
    ↓
链路层帧与调制解调器处理
    ↓
5G 无线编码、调制与物理传输
```

接收端执行相反过程：

```text
无线符号
    ↓
解码后的链路层数据
    ↓
IP 数据包
    ↓
UDP 数据报
    ↓
完成认证与解密的 QUIC 数据包
    ↓
QUIC 帧
    ↓
按序重组的 QUIC 流字节
    ↓
HTTP/3 消息体
    ↓
按声明的文件偏移写入对应区间
    ↓
恢复完整文件
```

## 2.1 封装

每一层通常把上层交付的数据视为本层载荷，并添加相应的协议头：

```text
[以太网/5G 相关元数据
  [IP 头
    [UDP 头
      [QUIC 头
        [加密后的 QUIC 帧
          [HTTP/3 数据
            [文件字节]]]]]]]
```

无线侧更底层的封装通常由调制解调器和 5G 网络完成。主机应用一般只能看到 UDP/IP 数据，而不会直接操作每个 5G PDCP、RLC、MAC 或物理层传输单元。

## 2.2 一个重要边界规则

不同协议层的边界不会保持一致。

一个文件区间可能被拆分成多个 HTTP/3 帧、QUIC 帧、QUIC 数据包和 UDP 数据报，并经过多次无线传输。反过来，一个 QUIC 数据包也可能携带多个帧，甚至包含多个 QUIC 流的数据。

因此：

> “文件块”“HTTP/3 消息体数据块”“QUIC STREAM 帧”“QUIC 数据包”“UDP 数据报”和“5G 无线传输块”是不同层次、不同含义的对象。

# 3. 一个文件从发送到还原的完整生命周期

本节沿完整的数据路径，说明文件如何从发送端应用程序进入网络，并在接收端还原为原始文件。

## 3.1 第一步：应用看到的是字节序列

文件在逻辑上是一个字节序列：

\[
F=[b_0,b_1,\ldots,b_{N-1}],
\qquad b_i\in\{0,\ldots,255\}.
\]

一个字节由 8 个比特表示，但应用程序通常处理字节，而不是逐个处理比特。

例如，ASCII 字符 `A` 的字节值为 65：

```text
十进制：65
十六进制：0x41
二进制：01000001
```

二进制文件不要求字节可打印。任何文件本质上都只是若干字节值按顺序组成的序列。

## 3.2 第二步：XQUIC 将文件划分为逻辑区间

当前应用协议使用：

```text
stream_range_size
```

划分文件区间。

例如：

```text
文件大小           = 1 GiB
stream_range_size  = 8 MiB
```

则应用会生成：

\[
\frac{1\ \text{GiB}}{8\ \text{MiB}}=128
\]

个逻辑区间。

第 \(k\) 个区间为：

\[
\begin{aligned}
\text{offset}_k &= k\times \text{stream\_range\_size},\\
\text{length}_k &= \min(\text{stream\_range\_size},N-\text{offset}_k).
\end{aligned}
\]

`stream_cnt` 通常不是区间总数，而是允许同时处理的请求数或流数上限。

例如：

```text
总区间数     = 128
stream_cnt   = 2
```

系统可以同时处理区间 0 和 1，然后处理 2 和 3，依此类推。

## 3.3 第三步：每个区间由一个 HTTP/3 请求/响应承载

对于 POST 上传：

```text
设备客户端 → 云端服务器
```

客户端在请求体中发送一个文件区间。

对于 GET 下载：

```text
云端服务器 → 设备客户端
```

客户端请求某个区间，服务器在响应体中返回该区间。

XQUIC 应用层协议使用如下自定义头部：

```text
x-stream-index
x-stream-count
x-stream-offset
x-total-length
content-length
```

这些头部用于告知接收方当前消息体在完整文件中的位置和长度。

## 3.4 第四步：HTTP/3 将消息体字节写入 QUIC 流

HTTP/3 通常把每组请求/响应映射到 QUIC 流。

从概念上看，发送端生成：

```text
流偏移 0          ───────────────►
[HTTP/3 头][消息体字节....................................]
```

QUIC 流是有序字节流，每个字节都对应一个流偏移。

如果某个消息体数据块从流偏移 100,000 开始，长度为 10,000，则其覆盖范围为：

\[
[100000,110000)
\]

## 3.5 第五步：QUIC 创建 STREAM 帧

QUIC 从流中取出部分字节，封装为 STREAM 帧：

```text
STREAM {
    stream_id,
    offset,
    length,
    fin,
    data
}
```

帧中的偏移使接收端即使面对乱序到达的数据包，也能将字节放回正确位置。

例如：

```text
数据包 X：流 8，偏移 0，    长度 1200
数据包 Y：流 8，偏移 2400，长度 1200
数据包 Z：流 8，偏移 1200，长度 1200
```

到达顺序可能是：

```text
X → Y → Z
```

但流的交付顺序会重组为：

```text
偏移 0 → 1200 → 2400
```

## 3.6 第六步：QUIC 构造数据包

QUIC 将一个或多个帧装入数据包。数据包包含：

- QUIC 头部；
- 数据包编号；
- 加密并认证的载荷；
- 一个或多个帧。

数据包编号属于数据包，而不属于流。

QUIC 的一项重要机制是：

> 发生丢包后，QUIC 会将仍需可靠交付的信息重新封装成帧，并通过具有新数据包编号的数据包发送。

因此，QUIC 通常不会逐比特原样重传旧数据包。

## 3.7 第七步：TLS 1.3 保护数据包

QUIC 集成 TLS 1.3，用于身份认证和密钥建立。

获得密钥后，QUIC 对数据包载荷进行加密和认证。网络中间设备可能看到部分路由相关信息，但无法读取应用数据。

概念上：

\[
\text{明文帧}
\overset{\text{AEAD}}{\longrightarrow}
\text{密文 + 认证标签}.
\]

若受保护的数据在传输中遭到篡改，认证通常会失败，相应数据包也会被丢弃。

## 3.8 第八步：QUIC 由 UDP 承载

QUIC 数据包成为 UDP 数据报的载荷：

```text
UDP {
    源端口,
    目标端口,
    长度,
    校验和,
    载荷 = QUIC 数据包
}
```

可靠性、拥塞控制、流、多路复用和安全性都由 QUIC 在 UDP 之上实现。UDP 本身不会重传丢失的数据报。

## 3.9 第九步：UDP 由 IP 承载

操作系统添加 IPv4 或 IPv6 头，其中包含源地址和目标地址。

在双 5G 客户端中，每个 UDP 套接字都绑定到指定的网络接口。绑定关系决定数据包经由哪张网卡和哪条运营商网络路径发送。

一条路径可以由如下网络四元组描述：

\[
(\text{本地 IP},\text{本地 UDP 端口},
\text{远端 IP},\text{远端 UDP 端口}).
\]

在多路径 QUIC 中，一条连接可以同时维护多个经过验证的网络元组。

## 3.10 第十步：调制解调器和 5G 网络发送编码后的无线符号

“文件最终以 0 和 1 传输”在概念上没有错，但在物理层并不完整。

调制解调器并不会把文件中的每个比特逐一直接放到无线电波上，而是执行以下处理：

- 信道编码；
- 速率匹配；
- 交织；
- 调制；
- 把编码比特映射为复数符号；
- 把符号映射到 OFDM 时频资源；
- 在网络分配的时频资源上发射。

根据调制方式，一个无线符号可以表示多个编码比特。

例如，高阶正交幅度调制会将多个比特映射为一个复数符号。实际调制编码方式会随无线信道条件变化，由 5G 系统动态决定。

因此，物理传输过程更准确地表示为：

\[
\text{数据包字节}
\rightarrow
\text{编码比特}
\rightarrow
\text{调制符号}
\rightarrow
\text{无线波形}.
\]

## 3.11 第十一步：接收端执行逆过程

接收端依次完成：

1. 无线系统解调并解码信号；
2. 调制解调器恢复链路层/IP 数据；
3. Linux 内核校验并处理 IP 和 UDP；
4. 将 UDP 载荷交给 XQUIC 套接字；
5. XQUIC 认证并解密 QUIC 数据包；
6. QUIC 解析各类帧；
7. 根据流 ID 和偏移放置 STREAM 数据；
8. HTTP/3 恢复请求体或响应体；
9. XQUIC 读取文件区间偏移；
10. 应用把字节写入输出文件相应位置。

## 3.12 第十二步：文件重建

假设两个区间并发到达：

```text
区间 0：文件偏移 0 MiB，长度 8 MiB
区间 1：文件偏移 8 MiB，长度 8 MiB
```

区间 1 完全可能早于区间 0 完成。接收端仍可直接把它写入正确位置：

```c
pwrite(fd, data, length, file_offset);
```

只有收到全部字节区间后，文件才算传输完整。

最终应在应用层执行完整性校验，例如：

```bash
sha256sum original_file
sha256sum received_file
```

哈希一致表示最终恢复的字节序列与原始文件完全相同。

# 4. QUIC 基础

QUIC 是一种构建在 UDP 之上的安全、可靠、多流传输协议。

## 4.1 为什么 QUIC 使用 UDP

以 UDP 为承载后，QUIC 可以在用户态实现传输协议功能，而不必完全依赖操作系统内核中的 TCP 协议栈。

这样可以实现：

- 更快的协议演进；
- 集成 TLS；
- 用户态丢包恢复；
- 多流；
- 连接迁移；
- 向应用暴露更多传输行为；
- 实验性的多路径扩展。

UDP 只负责承载数据报；通常由可靠传输协议提供的功能则由 QUIC 自行实现。

## 4.2 QUIC 连接

QUIC 连接是两个端点之间的逻辑安全关联。

一条连接包含：

- 密码学状态；
- 连接 ID；
- 数据包编号空间；
- 流；
- 流量控制状态；
- 丢包恢复状态；
- 一条或多条网络路径。

QUIC 连接并不只由固定 IP 地址和端口标识。连接 ID 使连接能够跨地址变化继续存在，并支持路径迁移和多路径操作。

## 4.3 连接 ID

连接 ID 是 QUIC 数据包头中的标识符。

即使网络四元组发生变化，它也可以帮助端点把到达的数据包关联到正确连接。

在多路径模式下，连接 ID 还可用于区分和管理不同路径上的数据包。

## 4.4 握手与 TLS

QUIC 握手建立：

- 对端身份，通常通过证书认证；
- 加密密钥；
- 传输参数；
- HTTP/3 应用层协议协商结果。

首次连接通常需要完整握手。会话恢复和 0-RTT 可以减少启动时延，但会增加部署复杂度和重放安全方面的考虑。

## 4.5 QUIC 流

QUIC 流是一段可靠、有序的字节序列。

不同流在交付层面相互独立：一个流发生丢包时，不一定会阻止另一个流继续交付数据。

但同一流内部仍按序交付。较低偏移的字节缺失时，后续字节可能暂时无法交给应用。

因此，在异构多路径传输中，使用多个文件区间流有助于减少单个超长流内部的乱序阻塞。

## 4.6 不存在跨所有流的传输层队头阻塞

TCP 只向应用提供一条有序字节流。一个 TCP 段丢失后，连接中其后的所有字节都可能被阻塞。

QUIC 提供多条流。流 A 上的丢包不必阻塞流 B。

但这不等于 QUIC 完全没有顺序等待：

- 同一流内字节仍有序；
- 应用可能要求多个流之间满足顺序；
- 文件重建可能等待所有区间；
- 多路径可能增加乱序到达。

## 4.7 数据包编号

QUIC 数据包编号用于：

- ACK；
- 丢包检测；
- 构造密码学 nonce；
- 在某个数据包编号空间中排序数据包。

数据包编号不是应用序号，也不是文件偏移。

## 4.8 ACK

接收端发送 ACK 帧，说明哪些 QUIC 数据包编号已经收到。

ACK 向发送端提供：

- 哪些数据包已到达；
- 哪些数据包可能丢失；
- 交付耗时；
- 已确认的数据量。

拥塞控制和丢包恢复高度依赖及时、正确的 ACK 处理。

## 4.9 丢包检测与重传

QUIC 通过数据包编号间隙和定时器检测丢包。

当某个数据包被判定丢失时，发送端识别其中哪些帧仍需可靠交付，并把等价信息装入新的数据包发送。

ACK-only 等不可重传信息会以不同方式处理。

# 5. HTTP/3 与文件传输

HTTP/3 是运行在 QUIC 之上的 HTTP 语义。

## 5.1 请求与响应模型

GET 事务：

```text
客户端请求头
        ↓
服务器响应头
        ↓
服务器响应体
```

POST 事务：

```text
客户端请求头
        ↓
客户端请求体
        ↓
服务器响应
```

## 5.2 为什么 GET 与 POST 的控制端不同

发送大批量消息体的一端，才是执行关键调度和拥塞控制决策的端点。

| 操作 | 主要数据发送端 | 控制大流量数据的调度器/拥塞控制 |
|---|---|---|
| POST 上传 | 嵌入式客户端 | 客户端调度器和客户端拥塞控制 |
| GET 下载 | 云端服务器 | 服务器调度器和服务器拥塞控制 |

修改客户端调度器，并不能直接控制服务器如何分配 GET 响应数据包。

## 5.3 基于区间的传输

本项目在 XQUIC 之上增加了一层应用级区间传输协议。

每个流携带文件中一段连续区间。接收端根据 `x-stream-offset` 和 `content-length` 放置数据。

优点：

- 多个区间并发；
- 可直接按偏移写入；
- 降低对单个超长有序流的依赖；
- 更容易按区间统计和重试；
- 可以实现流到路径的亲和性。

代价：

- 增加请求头和响应头开销；
- 占用更多流状态；
- 增加回调次数；
- 增加应用层调度开销；
- 可能增加文件 I/O 竞争。

# 6. XQUIC 提供了什么

XQUIC 是本项目采用的 QUIC/HTTP/3 协议栈。

应用程序负责提供配置和回调，XQUIC 负责处理传输协议逻辑。

## 6.1 主要组件

```text
应用程序
   │
   ├─ XQUIC 引擎 API
   ├─ HTTP/3 回调
   ├─ 套接字读写回调
   ├─ 定时器回调
   ├─ 调度器回调选择
   └─ 拥塞控制回调选择
        ↓
XQUIC 引擎
   ├─ QUIC 连接状态
   ├─ HTTP/3 状态
   ├─ 数据包构造
   ├─ 加密/解密集成
   ├─ ACK 处理
   ├─ 丢包恢复
   ├─ pacing
   ├─ 流量控制
   ├─ 路径管理
   └─ 流管理
```

## 6.2 引擎

XQUIC 引擎管理活跃连接和协议定时器。

应用通常执行：

1. 创建引擎；
2. 将收到的 UDP 数据报交给引擎；
3. 让引擎处理数据包并触发回调；
4. 通过应用提供的套接字回调发送 UDP 数据报；
5. 按 XQUIC 给出的定时要求唤醒引擎。

## 6.3 回调

XQUIC 采用回调驱动。

常见回调包括：

- 连接建立和关闭；
- HTTP/3 请求创建；
- 请求可读；
- 请求可写；
- 套接字写；
- 定时器调度；
- 日志；
- 路径创建/删除；
- 调度器操作；
- 拥塞控制事件。

回调必须尽快返回。耗时文件 I/O、编解码、推理、数据库操作或阻塞等待，应交给应用工作线程。

## 6.4 Libevent

`mini` 示例程序使用 Libevent 作为事件循环框架。

事件循环负责：

- 套接字可读事件；
- XQUIC 定时器唤醒；
- 内部通知；
- 连接推进；
- 应用任务完成。

事件循环线程一旦阻塞，由该线程负责的所有协议处理都会随之延迟。

## 6.5 线程所有权

较安全的模型是：

```text
网络接收线程或事件回调
       ↓
有界数据包队列
       ↓
单一 XQUIC 引擎线程
       ↓
有界应用队列
       ↓
应用/存储工作线程
```

除非某个 XQUIC API 明确支持线程安全，否则不要从任意线程并发调用同一个 XQUIC 引擎。

# 7. 多路径 QUIC 中的路径

在端点看来，路径是一条由本地与远端地址元组及其传输状态共同描述的网络通路。

对于嵌入式设备：

```text
路径 A：Qualcomm 调制解调器 A → 运营商 A → Internet → 云端
路径 B：Qualcomm 调制解调器 B → 运营商 B → Internet → 云端
```

## 7.1 每路径状态

每条路径可能维护：

- 本地与远端地址；
- 验证状态；
- 路径 ID；
- RTT 估计；
- RTT 方差；
- 拥塞窗口；
- 在途字节数；
- pacing 状态；
- 交付速率估计；
- 丢包统计；
- 活跃、备用、降级等路径状态。

## 7.2 路径验证

在新路径上发送普通应用数据前，协议必须确认路径可达，并确认对端确实存在于所声明地址。

通常通过 PATH_CHALLENGE 与 PATH_RESPONSE 完成验证。

## 7.3 异构路径

双 5G 路径是异构的，因为其属性不同且会独立变化：

\[
B_A(t)\neq B_B(t),
\]

\[
RTT_A(t)\neq RTT_B(t),
\]

\[
p_A(t)\neq p_B(t).
\]

设备移动时，较优路径也会变化：

\[
\arg\max_{r\in\{A,B\}} \text{quality}_r(t)
\]

随时间而变化。

因此，固定按 50/50 分流通常不是最佳策略。

# 8. 路径调度

调度器决定新的数据或恢复数据应通过哪条可用路径发送。

## 8.1 调度器输入

调度器可以观察每条路径：

\[
s_r(t)=
\{
RTT_r,\,
RTTVar_r,\,
cwnd_r,\,
inflight_r,\,
pacing_r,\,
deliveryRate_r,\,
loss_r,\,
pathStatus_r
\}.
\]

面向应用的调度器还可使用：

- 流优先级；
- 文件区间偏移；
- 剩余区间大小；
- 截止时间；
- 接收端缓冲区占用；
- 能耗；
- 运营商资费。

## 8.2 可用路径集合

调度器只能从当前可用的路径中进行选择。

一条路径通常只有在满足以下条件时才可发送：

- 已激活且已验证；
- 未被冻结，也未失效；
- 拥塞控制允许继续发送；
- pacing 允许当前发送；
- 满足抗放大限制；
- 应用策略允许使用。

定义：

\[
\mathcal A(t)=
\{r:\text{路径 }r\text{ 当前可发送}\}.
\]

调度器选择：

\[
r^*(t)=\pi(\{s_r(t)\}_{r\in\mathcal A(t)}).
\]

## 8.3 MinRTT

MinRTT 选择平滑 RTT 最小且当前可发送的路径：

\[
r^*=\arg\min_{r\in\mathcal A(t)} SRTT_r.
\]

优点：

- 计算开销极低；
- 能快速响应时延变化；
- 避免明显较慢的路径；
- 适合作为基线。

局限：

- 低 RTT 不代表高可用容量；
- 可能长期饿死高带宽但 RTT 稍大的路径；
- 未使用路径的测量可能陈旧；
- 不一定实现带宽聚合。

## 8.4 Backup

Backup 调度器优先使用主路径，同时保持另一条路径可用，以便在主路径失效或性能下降时接替传输。

优点：

- 性能稳定；
- 乱序较少；
- 处理开销较低；
- 适合接收端 CPU 受限场景。

局限：

- 正常情况下几乎不聚合带宽。

## 8.5 Balanced

Balanced 调度器通常尝试在路径间分配流量。

具体行为取决于实现，它可能平衡：

- 数据包数量；
- 字节数；
- 拥塞窗口利用率；
- 估计速率；
- 路径效用。

对异构路径而言，平均分配数据包或字节并不一定合理。

若：

\[
B_A=120\text{ Mbps},
\qquad B_B=40\text{ Mbps},
\]

则 50/50 分配可能压垮路径 B，同时未充分利用路径 A。

## 8.6 带宽感知调度

带宽感知调度器倾向于选择估计交付能力更强的路径。

最基础的评分：

\[
Score_r=\widehat B_r.
\]

更合理的最早交付评分：

\[
D_r=
t_r^{available}
+
\frac{Q_r+L}{\widehat B_r}
+
\frac{SRTT_r}{2}
+
\lambda RTTVar_r.
\]

随后选择：

\[
r^*=\arg\min_r D_r.
\]

该评分同时考虑带宽、当前积压、RTT 和时延波动。

## 8.7 ACT 与项目自定义调度器

`act`、`bw` 和 `balanced` 可能是 XQUIC 或本项目自定义实现的调度器。

名称本身不能完整定义其算法行为。工程师应检查：

- 路径评分公式；
- 使用哪些指标；
- 如何处理陈旧指标；
- 是否允许主动等待；
- 是否区分新数据与重传数据；
- 是否实现流或文件区间亲和性；
- 是否考虑接收端处理能力。

## 8.8 调度粒度

调度器可以按不同粒度工作：

- 数据包；
- QUIC 帧；
- 流；
- 文件区间；
- 流片段（flowlet）；
- 截止时间组。

逐包分流响应迅速，但更容易造成乱序。

按区间或流保持路径亲和性可以减少乱序，但对路径突变的响应较慢。

对于异构双 5G，较实用的设计通常包括：

- 短时间尺度上的数据包调度；
- 防止频繁切换的滞回机制；
- 在顺序代价较高时保持流/区间亲和；
- 路径故障或紧急重传时允许打破亲和性。

# 9. 拥塞控制

拥塞控制用于避免发送端压垮网络。

它与流量控制不同：

```text
拥塞控制：保护网络。
流量控制：保护接收端和应用。
```

## 9.1 核心变量

对每条路径 \(r\)：

- \(cwnd_r\)：拥塞窗口；
- \(inflight_r\)：已发送但尚未确认的字节数；
- \(pacingRate_r\)：允许发送的速率；
- \(SRTT_r\)：平滑 RTT；
- \(\widehat B_r\)：估计瓶颈带宽；
- \(p_r\)：观测到的丢包行为。

基于窗口的发送条件近似为：

\[
inflight_r + packetSize \leq cwnd_r.
\]

若采用 pacing，发送端还需要等待下一次允许发送的时间点。

## 9.2 CUBIC

CUBIC 是基于丢包的拥塞控制器。

它按照三次函数增大拥塞窗口，并在检测到拥塞丢包后缩小窗口。

优点：

- 应用广泛、行为易理解；
- 稳定的对照算法；
- 在许多高带宽网络上具有良好利用率；
- 解释相对简单。

在移动 5G 中的局限：

- 无线丢包或切换丢包可能被误判为拥塞；
- 容量骤变可能导致振荡；
- 丢包后的恢复可能慢于无线环境变化速度。

## 9.3 BBR

BBR 是基于网络模型的拥塞控制器。

它估计：

\[
\widehat B=\text{交付速率估计},
\]

\[
RTT_{prop}=\text{最小传播 RTT 估计}.
\]

随后依据该模型控制发送节奏（pacing）和在途数据量。

适用于移动路径的优点：

- 不直接由单个丢包事件主导；
- 能适应变化中的交付速率；
- 可为调度器提供速率信息；
- 通常适合高带宽路径。

局限：

- 若调度器长期少用某条路径，该路径估计会陈旧；
- 应用受限状态会影响交付速率估计；
- 两个独立 BBR 在共享瓶颈处可能相互作用；
- 探测周期可能造成突发或队列变化。

## 9.4 每路径独立控制

最简单的多路径设计是在每条路径上独立运行普通单路径拥塞控制器：

```text
路径 A → BBR 或 CUBIC 实例 A
路径 B → BBR 或 CUBIC 实例 B
```

当两条路径大体拥有独立瓶颈时，这种方式较合适。

两个不同 5G 运营商通常能提供较强路径独立性，但两条路径仍可能在以下位置汇聚：

- 云服务器接入链路；
- 同一个数据中心网卡；
- 共享对等互联；
- 接收端 CPU 或应用处理链路。

## 9.5 耦合式多路径控制

耦合式算法会跨路径使用信息。

典型算法包括 LIA、OLIA 及相关 MPTCP 拥塞控制。

其目标包括：

- 与单路径流量保持公平；
- 避免在共享瓶颈上过度激进；
- 把流量从较差路径迁移出去；
- 平衡响应速度与友好性。

当多条路径共享瓶颈时，耦合更有价值；若路径真正独立，则耦合可能过于保守。

## 9.6 当前系统的实用选择

对于接入不同运营商、设备持续移动且路径异构的场景，可以优先尝试：

```text
每路径独立 BBR
```

CUBIC 可作为对照。

LIA、OLIA 等耦合算法更适合用作：

- 公平性基线；
- 共享瓶颈替代方案；
- 研究扩展，而不是默认首选。

# 10. 调度器与拥塞控制的相互作用

两者在软件结构上分离，但会形成反馈闭环：

```text
调度器选择路径
        ↓
该路径发送数据包
        ↓
ACK 与丢包更新该路径的拥塞控制器
        ↓
cwnd、pacing 和速率估计发生变化
        ↓
未来的调度决策随之变化
```

## 10.1 可行动作集合的影响

拥塞控制会影响调度器的可选路径集合：

\[
\mathcal A(t)=
\mathcal A(\text{拥塞控制状态},\text{路径状态}).
\]

一条没有拥塞窗口余量的路径暂时无法被调度器选择。

## 10.2 测量反馈

调度器决定哪些路径真正获得流量，因此也决定哪些路径可以获得新鲜测量。

若 MinRTT 长期偏向路径 A：

- A 获得大量数据包和 ACK 样本；
- A 的速率估计持续更新；
- B 进入应用受限状态；
- B 的估计变陈旧；
- 调度器可能因此继续忽略 B。

这种循环会形成正反馈。

在移动场景中，调度器应定期探测低使用率路径，因为“较优路径”可能随位置变化。

# 11. 丢包恢复、重注入、冗余与 ACK

这些机制相关，但含义不同。

## 11.1 普通丢包恢复

当丢失数据包中承载的信息仍需可靠交付时，QUIC 会再次发送等价帧。

根据具体实现和调度策略，新数据包可以使用原路径，也可以使用另一条路径。

## 11.2 重注入

重注入（reinjection）是指改用另一条路径发送原路径上的待恢复数据。

例如：

```text
原始数据包：路径 A
检测到丢包/停顿
恢复数据包：路径 B
```

优点：

- 可更快从路径中断中恢复；
- 降低尾时延；
- 适合切换过程。

代价：

- 增加乱序；
- 增加 CPU 开销；
- 可能重复处理；
- 增加带宽消耗；
- 使 RTT 解释更复杂。

## 11.3 冗余发送

冗余发送是在普通丢包恢复尚未要求重传之前，就把同一份有效数据通过多条路径发送。

优点：

- 对关键数据可获得极低时延；
- 路径不确定时可靠性高。

代价：

\[
\text{有效吞吐效率}
=
\frac{\text{唯一有效交付字节}}
{\text{总发送字节}}
\]

会下降，因为重复数据占用了链路容量。

全量冗余只适合小规模或强实时数据，不适合普通大文件传输。

## 11.4 任意路径 ACK

某些多路径实现允许通过路径 B 确认经路径 A 收到的数据包。

这样可增强鲁棒性，但会让 RTT 测量更复杂，因为测得时延可能包含不同的正向路径和反向路径。

在受控实验中，同路径 ACK 更容易分析。

# 12. 流量控制与应用背压

拥塞控制保护网络，流量控制防止快速发送端压垮慢速接收端。

## 12.1 流级流量控制

每条流都有独立的发送额度。在接收端通告更多流量控制额度之前，发送端不能无限制地发送数据。

## 12.2 连接级流量控制

整条连接还拥有跨所有流的总接收额度。

## 12.3 应用消费速度非常重要

接收端通常会根据应用处理数据的进度，继续增加流量控制额度。

如果应用因为以下原因变慢：

- CPU 饱和；
- 同步存储写入；
- 回调缓冲区过小；
- 锁竞争；
- 队列拥塞；

则流量控制更新可能减慢甚至停止。

此时发送端看似受到网络限制，实际瓶颈却在应用处理环节。

## 12.4 接收端感知的容量上限

对于下载到嵌入式设备：

\[
G_{download}
\leq
\min\{
B_A+B_B,\,
C_{QUIC-RX},\,
C_{application},\,
C_{storage}
\}.
\]

只有接收处理链路能够承受聚合速率时，双路径才有实际收益。

# 13. 为什么上传和下载性能可能不同

即使使用相同的两条路径，上传能够聚合带宽也不意味着下载同样可以，因为发送端与接收端的角色已经互换。

## 13.1 上传

```text
嵌入式设备 → 云端
```

嵌入式设备负责：

- 读取文件；
- 生成 HTTP/3 请求体；
- 构造数据包；
- 加密；
- 调度；
- 拥塞控制；
- UDP 发送。

高性能云服务器负责高速接收。

## 13.2 下载

```text
云端 → 嵌入式设备
```

云服务器负责：

- 读取文件；
- 构造数据包；
- 调度；
- 拥塞控制；
- UDP 发送。

嵌入式设备负责：

- 两个接口的数据包接收；
- 内核到用户态数据拷贝；
- QUIC 认证与解密；
- ACK 生成；
- 丢包恢复；
- 流重组；
- HTTP/3 解析；
- 文件区间重建；
- 存储写入。

因此，即使无线网络可以提供更高下载速率，嵌入式接收端仍可能成为瓶颈。

## 13.3 发送端算法不同

上传性能主要由客户端调度器和客户端拥塞控制决定。

下载性能主要由服务器调度器和服务器拥塞控制决定。

进行方向对比时，必须记录实际数据发送端使用的配置。

# 14. 配置参数与理论概念的对应关系

本节解释主要配置项的理论含义。精确配置语法见《开发指南》。

## 14.1 `method`

```ini
method=GET
```

表示云端到设备的下载。

```ini
method=POST
```

表示设备到云端的上传。

它决定哪一端是大流量数据发送端。

## 14.2 `interfaces`

```ini
interfaces=rmnet_data0,usb0
```

指定客户端用于创建路径的网络接口。

单路径基准可使用：

```ini
interfaces=rmnet_data0
```



## 14.3 `stream_cnt`

该参数控制同时进行的 HTTP/3 区间请求上限。

较小值：

- 减少 CPU 与内存使用；
- 减少回调并发；
- 可能无法充分利用多路径。

较大值：

- 增加并发；
- 增加流状态与文件 I/O 竞争；
- 可能压垮能力有限的接收端。



## 14.4 `stream_range_size`

该参数是应用层文件区间大小。

区间较小时：

- 适应变化更快；
- 请求和头部更多；
- 回调与管理开销更高。

区间较大时：

- 开销更低；
- 流/路径亲和保持更久；
- 对路径质量突变的响应更慢。

建议实验值包括：

```text
4 MiB
8 MiB
16 MiB
32 MiB
```

最佳值取决于文件大小、移动变化时间尺度和设备处理能力。

## 14.5 `mp_sched`

该参数选择当前端点的调度器。

请牢记：

- POST 上传由客户端调度器控制；
- GET 下载由服务器调度器控制。



## 14.6 `cc`

该参数在解析器和端点支持的范围内选择拥塞控制。

当前代码主要支持：

```text
bbr
cubic
```

## 14.7 内核套接字缓冲区

```ini
kernel_sndbuf=...
kernel_revbuf=...
```

请求设置内核 UDP 发送/接收缓冲区。

较大的缓冲区可以吸收突发流量，但无法提升 CPU 的处理能力。缓冲区过大还可能掩盖排队和时延问题。

只有在套接字丢包统计或突发行为证明有必要时，才应增加缓冲区。

## 14.8 用户态缓冲区

```ini
user_send_buf_size=...
user_recv_buf_size=...
```

仅在代码实际读取这些配置时，才会影响应用层分块。

若某个回调使用硬编码固定缓冲区，则配置值不会生效。应检查源码确认。

## 14.9 `use_zlog`

详细逐包/逐事件日志可能显著降低嵌入式设备吞吐率。

性能测试时：

```ini
use_zlog=0
```

只在短时诊断运行中启用详细日志。



# 15. 配置策略

## 15.1 单路径参考

目的：确定每张网卡独立工作时能够达到的最佳速率。

```text
仅路径 A + BBR
仅路径 B + BBR
```

记录：

- 应用有效吞吐率；
- 线路速率；
- RTT；
- 丢包；
- CPU；
- 丢包计数器。

## 15.2 上传基线

数据发送端：嵌入式客户端。

建议从以下组合开始：

```text
客户端调度器 = MinRTT
客户端 CC     = BBR
stream_cnt    = 1 或 2
日志          = 关闭
重注入        = 关闭
```

随后再与自定义 balanced 或带宽感知调度器比较。

## 15.3 下载诊断基线

数据发送端：云服务器。

建议从以下组合开始：

```text
服务器调度器 = MinRTT
服务器 CC     = BBR
客户端接收端 = 丢弃或内存
stream_cnt    = 1
日志          = 关闭
重注入        = 关闭
任意路径 ACK  = 关闭
```

这样可将传输层性能与存储/应用处理分离。

## 15.4 下载聚合实验

确认接收处理链路具备足够的处理能力后，再使用以下配置：

```text
服务器调度器 = 带宽感知/最早交付
服务器 CC     = BBR
stream_cnt    = 2
区间大小      = 8–32 MiB
应用接收端    = 异步写线程
```

在完全相同条件下与 MinRTT 比较。

## 15.5 CPU 受限接收端

若一个或两个 ARM 核达到饱和：

- 使用 Backup 或 MinRTT，避免激进逐包分流；
- 降低 `stream_cnt`；
- 增大区间大小；
- 批量接收 UDP；
- 使用预分配队列；
- 关闭详细日志；
- 将存储写入移至另一线程；
- 选择性使用第二条路径，而不是持续满负荷使用。

网络算法无法突破接收端处理能力上限。

## 15.6 移动场景

进行移动实验时：

- 保持对两条路径的周期探测；
- 切换前使用滞回；
- 统一记录位置和时间；
- 不要因单个 RTT 样本立即切换；
- 区分短时衰落与持续降级；
- 测量切换恢复时间。

简单的滞回规则：

\[
D_{new} < (1-\eta)D_{current}
\]

其中，\(\eta\) 可从 0.05 到 0.10 的范围开始测试。

# 16. 如何在正确的层面测量性能

吞吐率只有在说明测量位置后才有意义。

## 16.1 无线/接口速率

从接口统计中测量：

```text
进入/离开 rmnet_data0 的字节数
进入/离开 rmnet_data1 的字节数
```

其中包含协议开销，也可能包含重传数据。

## 16.2 UDP 套接字速率

表示内核与用户态之间传递 UDP 数据报的速率。

它可能与无线接口速率不同，原因包括：

- 丢包；
- 封装开销；
- 调制解调器处理；
- 内核缓冲。

## 16.3 QUIC 唯一数据速率

表示新确认或新交付的流字节速率；统计口径正确时，不包含重复数据。

## 16.4 HTTP/3 消息体速率

表示交付给应用回调的消息体字节速率。

## 16.5 文件有效吞吐率

表示单位时间内成功写入或处理的唯一文件字节数。

若文件大小为 \(N\)，完成时间为 \(T\)：

\[
G_{file}=\frac{8N}{T}.
\]

这通常是用户最关心的性能指标。

## 16.6 为什么线路速率高而文件速率低

可能原因：

- 冗余发送；
- 重注入；
- 丢包；
- 乱序；
- 流内队头等待；
- 接收端 CPU 积压；
- 流量控制停顿；
- 存储写入；
- 应用队列。

因此至少应同时记录：

```text
每路径线路 Mbps
QUIC/HTTP3 交付 Mbps
文件有效吞吐 Mbps
各核 CPU
UDP/接口丢包
队列长度
RTT 与丢包率
```

## 16.7 因子组合实验

为区分调度器与拥塞控制：

```text
                   BBR        CUBIC
MinRTT              测试         测试
Bandwidth/ECF       测试         测试
Balanced            测试         测试
Backup              测试         测试
```

以下条件必须保持一致：

- 测试路线；
- 文件；
- 设备；
- 服务器；
- 流数量；
- 区间大小；
- 日志模式；
- 重注入模式。

# 17. 常见误解

## “两条 150 Mbps 路径一定能得到 300 Mbps”

不一定。聚合吞吐率受所有共享阶段中的最小能力限制：

\[
G_{dual}
\leq
\min\{
B_A+B_B,\,
C_{server},\,
C_{client},\,
C_{storage},\,
C_{application}
\}.
\]

## “调度器决定发送速率”

不直接决定。调度器负责选择路径，拥塞控制和发送节奏控制（pacing）决定该路径当前能否发送以及可以多快地发送。

## “拥塞控制与调度相互独立”

软件结构上应模块化，但测量、路径可用性与反馈会让二者相互作用。

## “RTT 低就代表路径最好”

低 RTT 表示时延可能较低，但不代表可用容量更大，也不代表当前一定可立即发送。

## “增加流数量一定提高吞吐率”

更多流可以增加并发，也会增加 CPU、内存、回调和 I/O 开销。

## “扩大套接字缓冲区能解决慢接收端问题”

它只能延后溢出，不能提高处理能力。

## “UDP 意味着应用数据不可靠”

UDP 本身不可靠，但 QUIC 在其上实现可靠性、ACK、丢包恢复和有序流。

## “QUIC 会重传同一个数据包”

QUIC 通常把丢失信息放入具有新数据包编号的新数据包，而不是原样重发旧包。

## “文件比特在无线链路上原样传播”

文件数据会经过加密、编码、交织和调制，映射为无线符号；接收端再逆向恢复原始字节。

## “上传与下载性能应该对称”

上传和下载的发送端、接收端、CPU 负载、调度执行端、ACK 行为与存储路径均不相同。无线链路对称并不意味着应用层有效吞吐率也对称。

# 18. 术语表

**ACK（确认）**  
说明哪些 QUIC 数据包编号已经收到的确认帧。

**AEAD（带关联数据的认证加密）**  
用于加密并认证 QUIC 数据包。

**Application-limited（应用受限）**  
发送端没有提供足够的数据来充分利用路径，导致带宽估计缺少有效样本的状态。

**Bandwidth-delay product，BDP（带宽时延积）**  
填满路径所需的在途数据量：

\[
BDP \approx bandwidth\times RTT.
\]

**BBR**  
基于交付速率与 RTT 估计的模型式拥塞控制器。

**CUBIC**  
采用三次函数增长拥塞窗口的丢包式拥塞控制器。

**Congestion window，`cwnd`（拥塞窗口）**  
窗口式拥塞控制允许在网络中未确认的最大数据量。

**Connection ID（连接 ID）**  
使 QUIC 能够在不依赖固定网络四元组的情况下识别连接。

**Flow control（流量控制）**  
保护接收端和应用，限制缓冲数据量。

**Goodput（有效吞吐率）**  
成功交付的唯一有效应用数据速率。

**HTTP/3**  
运行在 QUIC 之上的 HTTP。

**In flight（在途）**  
已经发送但尚未确认或判定丢失的数据。

**Jitter（抖动）**  
数据包时延或 RTT 的变化。

**Libevent**  
`mini` 示例程序使用的事件循环库。

**Multipath（多路径）**  
在同一逻辑传输连接中使用多条网络路径。

**Pacing（发送节奏控制）**  
按时间间隔发送数据包，而不是一次性突发发送整个拥塞窗口。

**Packet number（数据包编号）**  
QUIC 在某个编号空间中给数据包分配的序号。

**Path validation（路径验证）**  
确认网络路径可达且安全可用的过程。

**QUIC frame（QUIC 帧）**  
QUIC 数据包内的类型化信息单元，如 STREAM、ACK、PATH_CHALLENGE。

**QUIC packet（QUIC 数据包）**  
包含 QUIC 头部与加密帧的受保护传输数据包。

**Range（区间）**  
由一个请求/流传输的文件连续部分。

**Reinjection（重注入）**  
在不同于原始路径的路径上发送恢复数据。

**RTT（往返时延）**  
从发送数据到收到相应反馈所经历的时间。

**Scheduler（调度器）**  
选择出站数据所使用路径的模块。

**SRTT（平滑 RTT）**  
经过平滑处理的 RTT 估计。

**Stream（流）**  
QUIC 连接中的可靠有序字节序列。

**Stream offset（流偏移）**  
字节在 QUIC 流中的位置。

**UDP datagram（UDP 数据报）**  
承载 QUIC 数据包的 UDP 传输单元。

**Wire rate（线路速率）**  
在网络接口处测得的总流量速率，包含开销和重复数据。

**XQUIC**  
本项目采用的 QUIC/HTTP/3 协议栈。

## 最终认知模型

理解整个系统时，可以使用下列简化模型：

```text
应用程序决定数据的内容及其含义。
HTTP/3 组织请求与响应。
QUIC 提供安全流、可靠性、ACK 和路径管理。
调度器选择路径。
拥塞控制限定每条路径的发送能力。
UDP 和 IP 承载 QUIC 数据包。
调制解调器与 5G 网络把数据包比特变为编码后的无线符号。
接收端执行逆向处理，并根据偏移还原文件。
```

做性能工程时，始终先回答四个问题：

1. **哪一端正在发送大体量数据？**
2. **该发送端运行的调度器和拥塞控制是什么？**
3. **当前瓶颈位于哪一层？**
4. **测得的是线路流量、QUIC 交付、HTTP/3 消息体交付，还是完整文件有效吞吐率？**

这四个问题可以避免 XQUIC 实验中大多数配置错误和结果误判。
